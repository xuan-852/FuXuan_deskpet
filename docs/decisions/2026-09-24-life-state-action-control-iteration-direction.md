# 生命状态与动作控制中枢迭代方向

> **状态**：已确认的跨模块迭代方向；不是代码实现状态，也不是任务清单。
>
> **决策日期**：2026-09-24
>
> **用途**：作为“统一生命状态与动作控制中枢”后续迭代的方向入口。具体代码事实以 [`code-truth-architecture.md`](../code-truth-architecture.md) 和 [`docs/truth/`](../truth/) 中已验证文档为准；本文件不得把候选能力或历史计划写成已完成事实。
>
> **与产品方向基线的关系**：[`2026-09-15-product-direction-baseline.md`](2026-09-15-product-direction-baseline.md) 定义产品总目标与 L0-L6 边界；本文件聚焦其中 L3 身体能力、生命状态和动作控制的现实矛盾与推进顺序。

---

## 1. 最终目标

桌宠最终应像一个长期生活在桌面上的人：动作有生命感，回复具有稳定而独立的人格，并能可靠帮助用户完成工作。

本阶段的直接目标不是增加动作数量，而是建立一条可验证的闭环：

```text
模型真实能力
  -> 可组合动作能力
  -> 统一行为意图与控制中枢
  -> 身体/表情/注意力执行
  -> LifeState 回写
  -> 人格化回复与下一次行为
```

必须同时满足三项约束：

1. **能力先于意图**：中枢只能调度已经证明模型可见、语义成立、可复位的能力。
2. **证据先于暴露**：机械可写或视觉候选不能直接进入生产动作库、LLM 白名单或主动行为。
3. **恢复先于丰富**：任何新动作必须有取消、冲突、超时、退出和姿态复位路径。

## 2. 当前已完成的基础

截至本决策日期，以下能力已有代码或隔离验证证据，但完成程度不同：

- `LifeStateStore` 已提供在场、活动、注意力、情绪摘要和动作生命周期的有界、带 TTL 的只读快照。
- `EmbodiedEventStore`、`LifeTimelineStore`、`BodyStateStore` 和 `ExecutionMonitor` 已提供进程内观测，不保存原文、窗口标题、截图或网络数据。
- `CertifiedSkillRegistry`、`EmbodiedRuntimeAdmission`、`EmbodiedCoordinator` 已形成认证动作的登记、资源声明、准入、完成、取消、超时和抢占骨架。
- `BodyWriterInventory` 已登记认证动作、表情、旧动作、生成动作、空闲、步行、桌面物理、拖拽和内部提交层，并区分控制等级。
- `Live2DInputCoordinator` 已完成全局单租约、未知写入者拒绝、walking/drag handoff 和主要释放路径。
- walking、桌面物理、拖拽、表情和退出恢复已经有隔离 Player 或 EditMode 验收；真实鼠标 walking -> drag handoff 已有通过证据。
- 模型参数探针已经证明一批头部、身体、手臂、手型、脸部和效果通道可写、可见或可复位；这仍不等于语义认证。
- 当前模型已有呼吸、眨眼、眼球/头部/身体微动、天气联动、9 类空闲动作和若干认证/候选动作路径。

这些事实说明控制底座已经存在，但不能推导出“所有动作已经统一”或“模型已经具备真人级表达”。

## 3. 当前代码痛点与核心矛盾

### 3.1 控制中枢是两套体系的过渡态

认证动作走 `EmbodiedCoordinator`，表情、旧动作、生成动作、空闲、步行、桌面物理和拖拽主要走 `Live2DInputCoordinator`。后者已经有写入者登记和单租约，但不等于所有路径都经过统一的认证协调、语义优先级和行为意图。

结果是：系统能够较好地回答“当前谁占用输入”，还不能统一回答“为什么做这个动作、需要哪些模型能力、是否可以组合、应该如何被人格和生命状态调制”。

### 3.2 LifeState 主要是观测层，不是行为决策源

当前主要链路是：事件发生 -> LifeState 更新 -> 只读查询。尚未完整实现：LifeState -> 行为意图 -> 能力选择 -> 动作准入 -> 执行 -> 结果回写。

Attention 仍是有限字符串目标和 metadata；情绪、人格、最近行为历史与身体动作之间还没有一个统一的意图对象。

### 3.3 Renderer 仍承担过多职责

`Live2DRenderer` 同时处理模型加载、参数提交、行走姿态、空闲动作、表情、拖拽反馈、物理前置、动作恢复和测试入口。`ParameterCommitBridge` 是提交/审计边界，不代表参数写入者已经按行为来源完全拆分。

这会导致新增动作时必须同时理解渲染顺序、物理覆盖、租约、动作锁、旧参数清理和恢复路径，行为扩展成本高且容易产生“动作噪声”或残留。

### 3.4 参数数量大于有效表达自由度

当前映射表约 230 条，运行时探针发现约 244 个参数，但参数的真实状态分层如下：

```text
参数存在 != 可见
可见 != 语义明确
语义明确 != 可自然组合
可组合 != 已认证可生产
```

已有普查将参数分成姿态候选、效果参数、未分类可见参数和无可见证据参数；其中不少参数受 Cubism Physics 覆盖，或只有在组合动作中才有可读意义。

### 3.5 动作仓库的名义数量大于可靠资产数量

当前有 9 类空闲动作、MotionPlanner 模板、MotionTranslator 特殊模式、认证动作和多个探针候选。但模板、候选、机械序列和生产动作不是同一层级。

尤其是招手：`Param94 + Param99 + Param92` 已证明可以形成抬臂、手腕、手型的机械组合，但自然度和真实语义观看仍需独立认证。不能因为“参数能动”就把动作命名为招手并交给 LLM。

### 3.6 随机参数噪声还不是生命行为噪声

Perlin 呼吸、头身微动、眼球微动和随机眨眼已经提供基础生命感；随机空闲动作和行走停留也提供时间变化。但它们还没有统一受 LifeState、人格、情绪、最近行为、冷却和当前任务约束。

直接给参数叠加随机数会产生抖动、抢写和语义噪声，不能替代“有上下文、可恢复、低重复”的行为随机性。

### 3.7 验收擅长证明机械正确，不足以证明像人

当前测试能较好证明租约、冲突、释放、复位、退出和参数残留；对动作语义、节奏、起势、收势、重复感、人格一致性和语言/动作一致性的证据仍不足。

因此后续动作验收必须同时保留：机械、视觉、语义、时序自然度、恢复和交互冲突六类证据。

## 4. 模型能力边界

当前模型可以支持：

- 头部转动、倾斜和轻微偏转。
- 身体三轴侧倾或重心变化，但部分通道依赖物理写入顺序。
- 右臂抬起、部分左臂候选、手型切换和有限手腕变化。
- 眼睛、眉毛、嘴型、呼吸、眨眼和眼球微动。
- 头发、衣物、特效层的物理或表现反馈。
- 通过阶段曲线、保持、回落和参数组合构成短动作。

当前模型不能被假定支持：

- 真人级下肢骨骼动作。行走主要是桌面位移加身体步态，不等于真实腿部循环。
- 任意手指独立且清晰的手语。普通手指参数单独贡献弱，必须组合并人工确认。
- 任意参数自由叠加。物理覆盖、参数同帧写入和动作层互斥会改变结果。
- 仅凭参数名推断人体语义。左右、部位和效果归属必须以当前模型证据为准。
- 通过随机参数扰动自然地产生复杂人格行为。

因此动作能力必须以“参数集合 + 阶段序列 + 物理前置 + 复位策略 + 证据等级”登记，而不能只保存一个动作名称。

## 5. 后续迭代方案

### Phase 1：模型能力账本

**目标**：把“模型能做什么”变成可查询、可复核的事实。

**交付物**：

- 参数能力目录：部位、语义候选、运行时范围、物理依赖、可见性和复位结果。
- 组合约束表：可组合、冲突、覆盖和必须同步的参数组。
- 证据等级：`Unknown`、`Mechanical`、`Visible`、`SemanticCandidate`、`NaturalnessCandidate`、`Certified`、`Rejected`。
- 生产暴露字段：只有 `Certified` 能进入生产动作或 LLM 白名单。

**出口**：任何拟新增动作都能先查到所需能力、限制和证据缺口；不存在用参数名猜动作语义的路径。

### Phase 2：组合动作实验台

**目标**：用统一描述验证动作阶段和组合，而不是在 Renderer 中继续堆硬编码。

**交付物**：

- `prepare -> enter -> hold -> variation -> exit -> reset` 阶段格式。
- 运行时原生范围读取、baseline 捕获和完整恢复。
- 插值曲线、保持时间、局部组合和消融测试。
- 参数写入序列、复位误差、帧间跳变和截图证据。
- 只在隔离 `.test_mode` 使用，未认证候选不得进入生产或 LLM。

**第一批动作**：点头、轻微摇头、思考歪头、欢迎动作、招手候选、伸懒腰。

**出口**：每个动作至少通过机械、可见、语义、时序、复位和冲突六类检查，才能申请认证。

### Phase 3：少量高质量动作认证

**目标**：建立小而可靠的生产动作库，而不是扩大名义动作数量。

**交付物**：

- 每项技能的模型版本、映射版本、资源、前置姿态、进入/执行/收束/取消和失败降级。
- 可重复隔离 Player 证据和真实可见窗口人工记录。
- 认证动作与 LegacyCandidate、MotionMemory、LLM 暴露名单分离。

**出口**：认证动作能在 walking、drag、pause、cancel、timeout、exit 等关键边界安全收束，并且自然度达到既定门槛。

### Phase 4：行为噪声层

**目标**：把“随机”升级为受生命状态约束的自然不确定性。

分层实现：

- 基础层：呼吸、眨眼、眼球和低幅身体微动。
- 状态层：工作、空闲、夜间、疲惫和互动后的幅度/频率调制。
- 行为层：歪头、短暂停顿、回望、伸懒腰等短小认证行为。

**出口**：行为噪声有冷却、去重复、租约门控、可取消、可恢复，并能说明其 LifeState 触发条件；不允许逐帧随机写原始参数。

### Phase 5：统一 BehaviorIntent 与 LifeState 驱动

**目标**：让所有可见行为先提交统一语义意图，再由中枢决定是否和如何执行。

建议最小字段：

```text
intentId
source
semanticReason
priority
requiredCapabilities
resources
duration
interruptPolicy
recoveryPolicy
correlationId
```

**出口**：用户互动、空闲行为、认证技能、对话表情、工具反馈和行走状态都能关联到意图、执行结果和 LifeState 事件；失败能降级为文字/静默而不伪造身体成功。

### Phase 6：在证据充分后再评估资源级并行

候选方向包括“行走 + 注视”“身体动作 + 表情”“拖拽 + 面部反馈”。这不是当前默认目标。只有 Phase 1-5 建立能力和组合证据后，才评估从全局单租约迁移到有限资源层并行。

## 6. 决策规则

1. 不因参数数量、模板数量或单帧截图宣称表达能力完成。
2. 不新增动作名称，除非能力集合、阶段曲线、恢复路径和证据等级已登记。
3. 不把 `InputLeaseOnly` 或 `SemanticCandidate` 写成统一认证完成。
4. 不让 LLM 常规运行时写原始 `Param*` 或生成未经认证的裸关键帧。
5. 新能力先进入隔离实验台，再进入认证库，最后才允许行为层或 LLM 暴露。
6. 代码事实、决策方向和历史报告分层维护；发生冲突时停止实施并标记 `BlockedByDecision` 或 `BlockedByEvidence`。
7. 机械稳定性、自然度和人格一致性同等重要；任何一项缺失都只能标记为候选。

## 7. 明确非目标

本路线当前不承诺：

- 真人级肢体语言或真实下肢骨骼动作。
- 无限动作组合或任意模型参数自动理解。
- 立即启用资源级并行。
- 通用模型换装、任意 `.model3.json` 热插拔或跨模型自动迁移。
- 通过随机噪声替代动作设计、人格决策或情绪因果。
- 在没有人工/视觉自然度证据时扩大 LLM 动作白名单。

## 8. 后续任务的统一入口

后续涉及模型参数、动作、生命状态、输入租约、人格化身体表现的任务，必须先回答：

1. 依赖哪个已登记模型能力？
2. 是否需要新增组合能力或修改能力边界？
3. 由哪个 BehaviorIntent 发起，资源和中断策略是什么？
4. 取消、冲突、超时、退出和复位证据在哪里？
5. 完成后是 `Candidate`、`Certified` 还是 `BlockedByEvidence`？

回答不完整时，任务只能停留在设计或探针阶段，不得直接进入生产运行时。
