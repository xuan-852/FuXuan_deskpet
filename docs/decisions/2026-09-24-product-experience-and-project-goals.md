## 一、北极星目标与产品承诺

符玄桌宠不是“一个 Live2D 模型、一个聊天窗口和一组工具的拼接”，而是一个长期陪伴用户工作的桌面智能伴侣：

> **在不监视、不欺骗、不越权、不打扰用户的前提下，让用户感到符玄以连续、可理解、可中断、可恢复的方式存在于桌面上，并且能够可靠地帮助用户完成事情。**

理想中的符玄是：

> **一个安静但不冷漠、聪明但不冒进、能真正完成事情、会记得相处历史、能够根据有限且获授权的上下文调整表现，并且始终让用户知道她正在做什么的桌面智能伴侣。**

这里的“存在”“生命感”和“伴侣”是产品体验上的拟生命表达，不宣称真实意识、主观体验或无限环境理解。项目追求的是**可观察、可解释、可治理的连续行为**，而不是用拟人化台词掩盖系统事实。

### 1.1 三个核心体验结果

| 体验结果 | 用户应该感受到什么 | 不应退化为什么 |
|---|---|---|
| **陪伴存在感** | 她有状态、有反应、有节奏，并会在用户忙碌时保持克制。 | 随机动作播放器或持续打扰的“高存在感”助手 |
| **交互清晰感** | 用户可以自然地说话、点击、拖拽、查看状态，且始终知道当前发生了什么。 | 聊天记录、调试日志和工具状态堆在一起的操作面板 |
| **工作完成感** | 用户可以用自然语言交付目标，系统安全执行并交付真正可用的结果。 | 工具数量很多但需要用户记命令、猜进度或自行收拾结果的工具集合 |

三者不能彼此割裂。理想状态不是“聊天时是 AI、做工具时是脚本、待机时是动画”，而是**同一个符玄在不同情境下用不同方式帮助用户**。

### 1.2 关键术语边界

为了避免把不同问题混成“真实感”，本项目将其拆为三种可评估的质量：

- **事实诚实**：不伪造工具结果、不假装已经完成、不把猜测说成事实，并在失败或不确定时明确说明。
- **行为自然**：动作有起势、节奏、收势、冷却和恢复，不像参数随机抖动或机械循环。
- **角色可信**：人格、记忆、语气和长期行为保持连续，但不违背事实、安全和用户选择。

“生命感”是这三者在连续交互中的综合体验，不能用单帧截图、动作数量或参数数量单独证明。

## 二、目标层级与总体设计原则

本文件中的内容分为四层，发生冲突时不得把不同层级混为一谈：

1. **北极星目标**：项目最终要给用户什么体验。
2. **核心体验结果**：陪伴存在感、交互清晰感、工作完成感。
3. **横向质量原则**：安全、隐私、事实诚实、用户主体性、可恢复和长期稳定。
4. **技术约束**：事件、生命状态、意图、能力、仲裁、执行和结果回写的架构关系。

### 2.1 状态先于动作

任何明显的身体、表情、语音或主动行为，都应有可解释的状态和意图来源：

```text
BehaviorEvent
  → LifeState
  → BehaviorPolicy / BehaviorIntent
  → capability and resource arbitration
  → certified skill
  → synchronized presentation
  → result and state writeback
```

动作不是独立的动画播放，而是状态变化的表现结果。生命状态不能只作为事后日志，也应在允许的范围内影响下一次行为。

### 2.2 能力先于意图，证据先于暴露

系统可以有很多动作候选，但只有经过相应机械、视觉、语义、自然度、恢复和冲突验证的能力，才能进入生产默认路径、主动行为或 LLM 可调用白名单。参数可写、单帧可见或隔离实验通过，都不能单独证明能力已经成立。

### 2.3 事实诚实先于戏剧性

系统宁可明确告诉用户“当前不能执行”“结果尚未确认”或“动作已被打断”，也不能为了维持角色气氛而伪造动作开始、工具完成、文件生成或恢复成功。

### 2.4 用户主体性先于自主性

主动行为、记忆、感知和云端处理都必须服从用户的授权和可撤回选择。符玄可以主动提出低打扰建议，但不能把“像一个有生命的角色”解释成可以自行扩大权限、隐藏决策或拒绝用户停止。

### 2.5 人格服务于可靠性

角色表达可以影响语言、节奏、温度和表现风格，但不能绕过安全检查、认证准入、危险操作确认、隐私边界或事实反馈。

### 2.6 克制优于堆叠

高级感不来自动作数量、弹窗数量、颜色数量或 AI 调用数量，而来自正确时机和清楚边界。每次增加能力都要回答：

- 是否让用户更轻松？
- 是否让状态更清楚？
- 是否让陪伴更自然？
- 是否增加了噪音、性能负担、复杂度或不可控风险？

## 三、核心体验一：类似生命的模型生动感

### 3.1 目标定义

项目追求的是**可观察的拟生命体验**，而不是宣称模型拥有真实意识。生命感应来自：

```text
状态连续
反应有因
动作有节奏
表现有克制
被打断能恢复
内在状态与外在表现一致
结果会影响后续行为
```

用户应逐渐觉得“她在根据情况做出反应”，而不是“播放器正在随机播放动作”。

### 3.2 生命感的组成

#### A. 有状态

系统应逐步维护能够影响表现的状态，例如：

- 是否注意到用户，以及注意的置信度；
- 当前是否忙碌、等待、执行任务或处于恢复期；
- 是否刚被打断、抢占或拖拽；
- 当前精力与情绪倾向；
- 是否处于工作陪伴、安静或表达模式；
- 最近是否已经重复回应；
- 近期行为是否产生了需要短期处理的结果。

状态不必全部直接展示，但在需要时必须能够解释行为差异；不确定的推断不能当作绝对事实。

#### B. 有因果

每个明显行为都应能回答“为什么现在做这个”。例如：

- 用户点击或直接交互，可导致注意力转向用户；
- 用户说话，可导致回应、澄清或语音表现；
- 工具完成，可导致一次清楚但克制的完成反馈；
- 拖拽、新请求或高优先级任务，可导致当前动作中断并进入恢复；
- 自然循环只能产生低强度、无侵入的表现。

不接受无上下文的高频动作、动作与状态矛盾、以及被打断后继续写入旧动作。

#### C. 有节奏

生命感需要表现期、等待期、安静期、回应期和恢复期。生命感不是动作越多越好，而是在合适时机表现，在不需要表现时保持克制。

应支持：

- 用户交互后的短时回应窗口；
- 长时间工作时的低干扰陪伴；
- 重复交互的冷却、去重和降噪；
- 长时间无交互时的低强度自然循环；
- 工具执行期间不抢夺用户注意力；
- 安静模式、暂停和恢复后连续且可预测的状态转换。

#### D. 有恢复能力

动作、输入和任务随时可能被拖拽、新请求、应用暂停、资源冲突、初始化失败或系统退出打断。系统必须停止旧写入、释放资源、恢复安全姿态，并把完成、取消、抢占、超时或失败结果写回统一状态。

#### E. 表现与状态一致

状态不应只改变文字。允许的状态调制可以体现在动作选择、幅度、节奏、停顿、注视、主动频率和语言温度上，但必须通过已认证能力和统一仲裁实现，而不是由人格或 LLM 绕过身体安全边界直接写参数。

### 3.3 生命感的安全边界

生命感不得通过以下方式获得：

- 让 LLM 直接写 Live2D 原始参数；
- 大量随机参数抖动；
- 使用未经认证的动作制造“看起来像会动”；
- 多个未仲裁写入者同时修改同一资源；
- 用角色表现掩盖动作或工具失败；
- 把隐式监控、屏幕内容或剪贴板读取包装成“她在感知你”；
- 把“像问候”当作语义认证的替代品。

生命表现必须建立在：

```text
状态 → 意图 → 能力准入 → 安全执行 → 结果回写
```

### 3.4 评价问题

- 用户能否理解她为什么回应？
- 连续使用后是否仍然自然、不吵闹、低重复？
- 不同状态下是否有可感知但不过度的差异？
- 被拖拽、新任务或暂停打断后是否能安全且自然地恢复？
- 是否会把动作失败、工具失败或不确定性误表现为成功？
- 长时间运行后是否仍保持资源、姿态和状态一致？

## 四、核心体验二：对话 UI 的优雅与清晰

### 4.1 目标

对话 UI 不只是把聊天记录放在模型旁边，而应让用户感到：

```text
轻、静、清楚、有层次、不打扰工作、随时可以接近。
```

优雅感来自信息组织、节奏、可读性和克制，而不是装饰堆叠。所有状态都必须可读，不能只靠颜色、动画或角色台词表达。

### 4.2 设计要求

#### A. 轻量

- 默认占用空间小；
- 不必要的信息自动收起；
- 重要内容可以展开；
- 不因为每条消息都弹窗；
- 用户主动交互时提供完整信息，用户工作时退到背景；
- 不用视觉动效迫使用户关注非关键状态。

#### B. 有层次

至少要清楚区分：

- 角色回应；
- 用户输入；
- 工具执行状态；
- 任务进度与排队；
- 用户确认与审批；
- 警告、失败、取消和恢复建议；
- 最终产物与路径；
- 历史内容和调试信息。

普通聊天应轻量，工具执行应透明，危险操作应明确，失败应可行动。调试信息不能污染普通用户的主要阅读路径。

#### C. 有节奏

支持流式输出、逐句显示、工具中间状态、最终结果和结果回顾，但不将进度动画变成新的噪音。用户应能理解：

```text
正在理解 / 正在调用工具 / 工具已完成 / 正在整理 / 可以继续交流
```

#### D. 角色与功能一致

界面可以体现符玄的克制、清雅、秩序感和少量仪式感，但必须服从可读性、可操作性和事实反馈。不能用角色台词掩盖错误，也不能为了“像角色”牺牲操作清楚度。

### 4.3 关键场景

- **普通聊天**：用户能自然输入、阅读回应并继续追问，历史和当前内容边界清楚。
- **工具执行**：界面说明正在处理什么、当前阶段、是否需要确认、是否可以取消，以及最终产物在哪里。
- **长任务**：任务有开始、进度、排队、取消、完成和失败状态；已经完成的部分不因后续失败而消失。
- **工具失败**：不只显示“失败”，而要说明发生了什么、已完成什么、未完成什么以及下一步可以怎么做。
- **多任务**：用户能区分当前任务、排队任务、已取消任务和已完成结果，不会丢失输入或误以为任务仍在运行。

### 4.4 评价问题

- 用户能否快速找到输入入口并理解当前状态？
- 是否能区分聊天、工具、审批、错误和结果？
- 工具状态是否透明但不打扰？
- 长文本、路径、进度和错误是否容易阅读？
- 错误是否可理解、可行动、可追踪？
- 角色风格是否服务于可用性，而不是遮蔽事实？

## 五、核心体验三：工具调用的实用与完成

### 5.1 目标

工具价值不在于数量，而在于用户可以用自然语言表达目标，系统选择合适能力，安全执行并交付可用结果。

```text
用户表达任务 → 系统理解目的 → 选择能力 → 安全执行 → 验证结果 → 交付与回顾
```

用户不应需要记工具名、端点名或内部工作流。

### 5.2 设计要求

#### A. 任务中心，而非工具中心

用户说“帮我整理资料”或“帮我做一份汇报”，系统内部可以调用多个工具，但对外呈现为一个可理解的任务过程，而不是工具名列表。

#### B. 工具选择可靠

选择工具时考虑：

- 用户真正意图；
- 工具能力边界；
- 输入是否完整；
- 是否需要确认；
- 操作风险和副作用；
- 是否存在更简单、可逆或本地的路径。

“工具存在”不是调用它的理由；无法确认意图时，应先澄清或选择安全的只读路径。

#### C. 结果真正落地

成功不能只由 API 的 `success=true` 定义，还要确认：

- 结果是否生成；
- 文件或记录是否落在正确位置；
- 输出是否能打开或继续使用；
- 用户是否知道路径、内容和限制；
- 部分失败、降级或未验证部分是否被说明。

**身体动作、完成音效或角色台词都不能作为工具成功的证据。** 工具事实和产物状态才是成功依据。

#### D. 安全而不烦琐

低风险查询应保持流畅；文件、网络、系统设置和危险操作应按风险分层处理。高风险操作要在执行前说明影响、请求确认并提供取消路径，但不能让所有小操作都弹确认。

#### E. 可恢复

工具失败时应尽量支持重试、备用方案、继续未完成部分、保留已完成结果和补充输入，而不是伪造成功、重复副作用或吞掉错误。

### 5.3 评价问题

- 用户是否需要记工具名称？
- 一句话任务能否被正确理解，缺少信息时是否会澄清？
- 工具调用是否透明且风险适当？
- 危险操作是否有适当确认和取消？
- 结果是否真的交付并可继续使用？
- 失败后用户是否知道怎么办，且不会误以为已经完成？

## 六、可靠感、用户主体性与隐私边界

可靠性是生命感、UI 和工具实用感的共同基础。系统必须逐步提供：

```text
可预测、可解释、可取消、可恢复、可追踪。
```

### 6.1 可预测与可解释

用户应逐渐知道点击、输入、长任务、拖拽和取消会发生什么。关键时刻要说明：

- 为什么没有执行；
- 为什么需要确认；
- 为什么动作或任务被打断；
- 为什么工具失败或暂时不能回应；
- 当前结果是否已经验证；
- 下一步可以做什么。

不要求展示全部内部推理，但必须提供足够的行为原因、状态来源和结果事实。

### 6.2 用户主体性与同意

用户应能够在可理解的位置控制：

- 是否启用主动行为以及主动频率；
- 是否进入安静、暂停或游戏等模式；
- 是否启用某类环境感知；
- 是否保存某类记忆；
- 是否允许云端处理；
- 是否查看、删除或清理记忆和任务记录；
- 是否停止聊天请求、工具任务、身体动作和排队工作。

“可取消”不仅是 UI 元素消失，必须有真实的底层停止语义；无法立即停止时，要明确说明当前边界。

### 6.3 最小必要感知

感知的目的是调整陪伴方式，不是扩大监视范围。允许使用的上下文必须满足：**明确授权、确有必要、最小化、本地优先、可解释、可撤回**。

优先使用：

- 用户对桌宠的点击、拖拽、停留和直接输入；
- 用户主动设置的工作、会议、游戏、安静等模式事件；
- 时间、天气、系统负载等确有必要且可解释的本地状态；
- 经过用户授权的最小化活动信号，并以置信度而非绝对事实使用。

默认不得通过以下方式制造“聪明感”：

- 读取屏幕内容、截图或游戏内容；
- 读取窗口标题、浏览器标签或剪贴板内容；
- 记录完整键盘输入、鼠标轨迹或与任务无关的行为细节；
- 将未授权的前台活动监控作为陪伴的默认基础。

如果未来确实需要扩大感知范围，必须单独定义授权、数据最小化、保留期限、关闭方式和降级行为，不能由实现自行扩张。

### 6.4 可恢复与可追踪

应用暂停、网络失败、工具失败、动作中断、Renderer 重建或系统退出后，应尽量：

- 保留已完成内容；
- 回到安全状态；
- 避免重复副作用；
- 释放资源与旧写入者；
- 告诉用户当前状态和下一步。

重要行为应有可复现的事件、资源释放、状态回写、失败和取消证据；“代码能编译”“接口返回成功”“动画看起来播放过”都不能单独代表交付完成。

---

## 七、连续性、记忆与人格可信度

符玄不应只是通用助手换了一层外观。长期陪伴的关键不是记得越多，而是让用户感到：**今天的符玄和昨天的符玄是同一个存在，同时允许用户纠正她。**

### 7.1 连续性目标

应逐步形成：

- 跨会话的稳定身份和角色边界；
- 重要事实、偏好和计划的可治理记忆；
- 近期事件对短期表现的合理影响；
- 人格稳定但不僵化的表达方式；
- 可解释的情绪回落和行为冷却；
- 记忆错误、冲突和不确定性的纠正路径。

记忆不等于事实。低置信度推断必须保留不确定性，不能在语言、动作或工具决策中被当作已确认信息。

### 7.2 人格可以影响什么

人格、关系和短时情绪可以影响：

- 语言风格、称呼与表达长度；
- 回应温度、停顿和解释方式；
- 主动提醒频率；
- 已认证动作的选择倾向、幅度和节奏；
- 对用户历史的连续感。

### 7.3 人格不能影响什么

人格、关系和情绪不能决定：

- 是否绕过安全检查或隐私边界；
- 是否绕过认证准入和资源仲裁；
- 是否执行危险操作而不确认；
- 是否把猜测说成事实；
- 是否伪造任务成功、文件生成或动作完成。

---

## 八、感知、主动行为与陪伴节奏

主动行为应是低打扰、可配置、可解释的陪伴策略，而不是一个不断触发动作的定时器。

### 8.1 主动行为的基本原则

- 用户交互、高优先级任务、拖拽和输入期间优先保持安静；
- 工作、会议、游戏或安静模式抑制主动行为；
- 用户长时间工作时可以提供低频、低强度、可取消的陪伴；
- 用户重新关注时可以恢复短时回应，但应受重复冷却约束；
- 断网或云端不可用时，主动行为仍应安全地本地降级；
- 主动行为应能说明触发原因、使用的信号和当前抑制原因。

### 8.2 主动行为预算

主动性应由多个因素共同约束，而不是由单一间隔决定：

```text
主动频率
× 当前模式
× 用户最近互动
× 状态与精力
× 最近重复惩罚
× 冷却时间
× 当前资源占用
× 打扰风险
```

可提供 Quiet、Balanced、Expressive 等行为画像，但任何画像都不能绕过安全、隐私、用户暂停和高优先级交互。

### 8.3 低确定性时的降级

当系统无法确认用户是否在场、是否忙碌或是否希望被打扰时，应选择低强度、可取消、不会产生副作用的行为，而不是通过更多感知或更高频表现来“猜得更准”。

---

## 九、工具状态与生命表现的统一

工具执行和角色表现不应完全割裂，但也不应让每次工具调用都变成表演。正确原则是：

> **工具状态进入统一生命状态；生命状态可以调制表现强度；表现不能冒充工具结果。**

理想过程是：

```text
用户提出任务
→ 符玄说明开始处理
→ UI 展示任务状态
→ 桌宠进入专注或低干扰状态
→ 工具执行并验证结果
→ 完成或失败反馈
→ 回到合适的陪伴状态
```

设计要求：

- 工具状态可以影响安静程度、注意力和表现强度；
- 工具执行期间不因动画、主动聊天或装饰抢夺注意力；
- 工具完成可以有一次清楚但克制的反馈；
- 工具失败优先诚实解释，不用情绪、动作或角色台词掩盖；
- 任务结果必须由工具事实、产物状态和验证结果确认。

---

## 十、标准体验场景

上层目标不直接规定实现任务，但应通过少量标准场景检验不同目标是否真的统一：

### 10.1 用户重新关注桌宠

用户一段时间后点击或直接与桌宠交互。理想体验是：

```text
交互进入统一状态
→ 注意力转向用户
→ 生成可解释的回应意图
→ 语言、注视和短动作属于同一回应
→ 用户继续拖拽或输入时可以立即打断
→ 结果回写并影响短期冷却或下一次回应
```

不可出现：动作无原因、语言与身体矛盾、被打断后旧动作继续写入。

### 10.2 长任务执行

用户请求搜索、整理、生成或办公任务。理想体验是：

```text
说明任务目标
→ 展示当前阶段
→ 必要时请求确认
→ 执行期间保持低干扰
→ 支持取消或说明不可立即取消
→ 交付已验证结果和路径
→ 失败时保留已完成部分并说明下一步
```

不可出现：无进度、无结果路径、假装完成或因角色表演掩盖失败。

### 10.3 动作中被打断

动作进行中收到拖拽、新任务、暂停或退出。理想体验是释放旧资源、停止旧写入、恢复安全姿态、记录真实终态，并由新的高优先级行为接管。

不可出现：卡死、奇怪姿势、状态已完成但模型仍运动、旧写入者残留。

### 10.4 用户处于忙碌或安静状态

用户通过明确模式，或通过经过授权且低置信度的活动信号表现出不适合被打扰的状态。符玄应降低主动行为，保留低强度生命循环，等待用户重新接近。

不可出现：为了证明“有生命”而持续弹窗、说话或抢占输入。

### 10.5 网络或工具不可用

系统应优先使用本地安全降级，不能伪造云端结果；需要用户补充信息时清楚说明，不把失败包装成角色剧情。

### 10.6 跨会话回来

符玄可以使用经过治理的长期记忆保持关系连续，但应尊重记忆置信度、用户修改和删除，不应突然主动暴露不必要的历史细节。

---

## 十一、审美与技术克制

项目的高级感来自克制：

```text
不滥用动画
不滥用弹窗
不滥用颜色
不滥用 AI
不滥用工具
不滥用人格表达
不滥用权限和感知
```

新增能力前应确认它是否带来真实价值，是否增加噪音、性能负担、复杂度、隐私暴露或不可控风险。任何“为了看起来更聪明、更像人”而增加的能力，都必须先证明不会损害事实诚实、用户主体性和工作完成。

---

## 十二、目标优先级与冲突处理

当目标发生冲突时，按以下顺序取舍：

1. **安全、隐私与明确授权**；
2. **事实诚实、结果可验证与可追踪**；
3. **用户主体性、可取消与可恢复**；
4. **任务可靠、结果可交付与副作用可控**；
5. **信息清楚、交互可用与可访问**；
6. **连续性、自然度、人格表现与陪伴节奏**；
7. **视觉优雅、仪式感和戏剧性**。

因此：

- 拟生命体验不能建立在不可靠或未授权感知之上；
- 自然度不能高于事实诚实和可控性；
- 优雅不能牺牲可读性和任务完成；
- 人格不能掩盖错误；
- 主动性不能打扰用户或阻断高优先级交互；
- 动作数量不能替代动作语义、恢复和证据；
- 更强的自动化不能成为扩大权限的理由。

---

## 十三、明确反目标

本项目不以以下方向为目标：

- 不是动作数量最多的 Live2D 播放器；
- 不是宣称模型拥有真实意识或无限环境理解的拟人系统；
- 不是让 LLM 直接控制身体参数的开放实验场；
- 不是工具数量越多越好的工具集合；
- 不是要求每次工具调用都播放动作的表演系统；
- 不是用屏幕、窗口标题、剪贴板或隐式监控制造“聪明感”；
- 不是用复杂 UI 展示所有内部日志；
- 不是持续主动打扰用户的“高存在感”助手；
- 不是用角色台词、情绪或动画掩盖事实错误；
- 不是把未经认证的候选能力包装成正式能力；
- 不是用随机抖动假装生命感；
- 不是为了追求功能数量而牺牲安全、隐私、性能、可维护性和用户控制。

---

## 十四、长期评价维度与迭代出口

后续功能评审和迭代出口应分别关注体验结果、质量原则和证据，不用单一“完成度”替代判断：

| 维度 | 核心问题 |
|---|---|
| **生命感** | 表现是否有状态、有因果、有节奏，且能被打断和恢复？ |
| **自然度** | 动作是否有明确语义、起势、保持、收势、低重复和状态一致性？ |
| **对话清晰** | 信息是否清楚、克制、易读，并能区分聊天、工具、审批、错误和结果？ |
| **工具实用** | 用户是否能少记命令，真正拿到可验证、可继续使用的结果？ |
| **可靠可控** | 是否可预测、可解释、可取消、可恢复、可追踪？ |
| **用户主体性** | 用户能否控制主动行为、感知、记忆、云端处理和暂停状态？ |
| **角色连续** | 长期相处中人格、记忆、情绪回落和表达方式是否连续可信？ |
| **感知边界** | 是否只使用必要、获授权的信息，并在不确定时安全降级？ |
| **技术克制** | 是否避免不必要的复杂度、噪音、性能负担和未经证明的能力？ |
| **证据质量** | 重要结论是否有可复现的运行时、视觉、语义、恢复和冲突证据？ |

后续可以在模块级文档或验收协议中为这些维度设置量化门槛；本文件只定义方向和评审问题，不把历史评分自动视为当前验收结果。

任何新功能至少应说明：

1. 它改善了哪一项核心体验；
2. 它依赖或改变了哪些状态、能力和权限；
3. 它引入了什么安全、隐私、性能或复杂度风险；
4. 用户如何停止、查看、修改或撤回它；
5. 如何验证成功、失败、取消、恢复和长期行为；
6. 与其他目标冲突时服从哪条优先级。

---

## 十五、与后续架构迭代的关系

本目标文档不规定每个类的实现，但为架构演进提供方向：

```text
事件层
  ↓
生命状态层
  ↓
行为策略与意图层
  ↓
能力与资源仲裁层
  ↓
认证技能执行层
  ↓
同步表现层（身体 / 表情 / 注意力 / UI / 语言）
  ↓
结果、经验与状态回写层
```

后续迭代应优先建设能够同时支撑三大核心体验的公共能力：

- 统一事件和生命状态；
- 可解释的 `BehaviorPolicy` 与 `BehaviorIntent`；
- 可取消、可恢复、可追踪的执行句柄；
- 认证技能、资源仲裁和安全收束；
- 对话、工具和身体表现的状态同步；
- 统一结果回写、失败降级和记忆治理；
- 用户可控的主动行为、感知和隐私边界；
- 可复现的运行时、视觉、语义和长期行为证据。

本文件定义的是方向、边界和判断标准。具体实现必须以代码真相、批准指导文档、任务包和实际验证结果为准；本文件中的“应当”不等于当前项目已经完成。
