# 文档治理与任务分发规范

> **状态**：已确认的全局决策。
>
> **适用范围**：所有新功能、重构、验收、外部资料引用和执行代理任务。
>
> **上位决策**：[产品方向基线](2026-09-15-product-direction-baseline.md)。本文件规定工作方式，不记录任何功能已经实现的事实。

## 1. 目的与非目标

**DG-01**：让后续代理能快速找到当前方向、允许范围和可验证目标，且无法用手工状态表掩盖事实漂移。

**DG-02**：将“期望如何实现”与“代码目前如何运行”隔离；前者可讨论，后者必须有构建、测试或可复核证据。

**DG-03**：方向冲突时停止实施并交由人工决策，避免以覆盖代码或回退 Git 的方式掩盖冲突。

非目标：本规范不替代具体功能指导文档，不赋予执行代理扩大权限，也不把旧文档自动认定为新架构下的代码真相。

## 2. 目录即状态

| 路径 | 唯一职责 | 状态如何得出 |
|---|---|---|
| `docs/decisions/` | 跨模块、长期产品与工程决策 | 决策记录本身；被新决策取代时保留并链接替代项 |
| `docs/guides/proposed/` | 未批准或仍在讨论的功能指导 | 位于 `proposed` |
| `docs/guides/approved/` | 可用于任务下发的功能指导 | 位于 `approved` 且通过 DG-11 完整性检查 |
| `docs/truth/` | 已验证的代码/运行时事实 | 只接受测试或可复核证据支撑的内容 |
| `docs/archive/` | 已被替代的计划、报告和历史材料 | 位于 `archive`；保留替代链接与原始结论 |
| `tasks/packages/` | 可下发给执行代理的机器可读任务包 | 包文件存在且引用一份批准指导文档 |
| `docs/generated/` | 由脚本生成的导航和检查结果 | 禁止手工编辑 |
| `docs/templates/`、`tasks/templates/` | 模板，不代表功能状态 | 始终排除在状态统计外 |

旧 `docs/modules/`、`docs/code-truth-architecture.md`、路线图和报告在逐份迁移、复核前保留原角色；它们不能仅凭名称被视为 `docs/truth/`。

## 3. 指导文档契约

**DG-10**：每项指导文档必须声明其上位决策、范围与非目标，使用稳定需求 ID（如 `FR-01`、`C-01`、`AC-01`）。

**DG-11**：一份文档只有同时具备以下字段，才可移入 `approved/`：

1. 目标和非目标；
2. 功能需求与公开接口；
3. 硬约束（安全、隐私、成本、兼容性）；
4. 状态/数据/并发与失败恢复（适用时）；
5. 自动或可复核的验收证据；
6. 允许修改范围与明确不允许范围；
7. 对应代码真相、决策和依赖文档链接。

**DG-12**：涉及多组件、公共接口、共享数据、状态机/持久化、权限/隐私/云端成本、不可逆副作用或多链路验收的事项，必须使用扩展指导文档。简单单组件事项可写入所属模块指导文档，但仍需满足可追溯和验收要求。

模板见 [功能指导文档模板](../templates/feature-guide.md)。

## 4. 任务包与执行边界

**DG-20**：一个任务包只对应一个主批准指导文档和一个独立验收目标。跨指导文档的联动先建立集成指导文档。

**DG-21**：任务包必须机器可读，并包含：主指导文档、需求/验收 ID、允许路径、禁止路径、验证命令、预期代码真相文档、证据产物和风险级别。模板见 [任务包模板](../../tasks/templates/task-package.example.json)。

**DG-22**：执行代理只能修改任务包允许路径；不得修改全局决策、批准指导文档、任务包范围外代码、生成文档或验收结论。其交付物是差异和证据，不是“完成”声明。

## 5. 冲突、外部资料和验收

**DG-30**：代码真相、批准指导文档与全局决策发生方向冲突时，立即停止实现，记录 `BlockedByDecision`：冲突来源/需求 ID、影响、选项、建议和等待的人工决定。不得通过静默修改其中任一方消除冲突。

**DG-31**：外部资料必须提供确定 URL、访问/验证日期、原始主张与引用用途。执行代理提交的资料须由主代理复核；资料不足则 `BlockedByEvidence`。

**DG-32**：验收由主代理对照指导文档、实际差异和证据进行。测试未通过、被环境阻断或证据缺失时只能标为“未验证/受阻”，不得写入代码真相为“已实现”。

## 6. 自动生成与人工边界

**DG-40**：`node scripts/docs/generate_document_map.cjs` 扫描规定目录并生成 `docs/generated/document-map.md`。它从路径推导分类/状态，并列出任务包引用关系；生成结果不允许手工编辑。

**DG-41**：生成索引是导航与一致性检查，不替代人工产品决策或代码验收。脚本发现任务包指向不存在或非 `approved` 指导文档时，必须以非零退出码失败。

## 7. 推进顺序

1. 建立本规范、模板、任务包格式和生成索引；
2. 建立 L1–L6 的批准指导文档，先完成 L1/L2/L3；
3. 为每份旧文档标注保留、迁移或归档去向，更新链接后再移动；
4. 在第一份批准指导文档完整后，才下发实现任务包；
5. 每项实现后以测试证据更新代码真相，并重新生成索引。
