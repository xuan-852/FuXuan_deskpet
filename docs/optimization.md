## 一、当前基线

当前主要风险不再是“约 5 元/天”的 Key 归属问题。该费用已确认来自其他项目复用同一个用户级 `DEEPSEEK_API_KEY`，后续仍应使用按项目隔离的 Key 和账单记录。

## 二、优化原则

1. 先消除状态和资源生命周期风险，再做性能和结构重构。
2. 云端调用、Token、记忆写入和危险工具必须有明确边界，不能用“看起来没问题”替代测量。
3. 每次只改一个责任边界；partial 拆分必须保持公开 API 和执行顺序不变。
4. 先用隔离数据目录测试，再运行完整播放器；测试失败时不更新“已验证”文档结论。
5. P0 安全网、危险工具审批、Live2D Physics 顺序和外置窗口销毁顺序不为追求整洁而迁移。

## 三、下一阶段计划

### P0：稳定性和可恢复性

| 方向 | 具体工作 | 验收标准 |
|------|----------|----------|
| 桥接请求边界 | ✅ 已完成第一步：统一 `ConfigureRequest()` 的鉴权、JSON 请求头和 timeout；后续仍可继续整理响应读取和 correlation id | 不改变端点响应；HTTP 错误、超时、空响应均有稳定错误文本；Node 语法和 C# 构建通过 |
| 任务状态机 | 明确 queued/running/done/error/cancelled 的状态转移，补充重复取消、退出中取消、取消后迟到响应处理 | 退出时不再继续轮询；取消接口返回 false 时上层不会误报成功 |
| 外置窗口 | 增加真实可见播放器下的启动、隐藏、恢复、关闭多轮回归 | 不出现窗口线程残留、透明窗口消失或退出崩溃；不能只用强制杀进程作为通过依据 |
| 测试产物 | 修复或替代 EditMode XML 不刷新的问题，保留明确的测试时间、用例数和退出码 | 每次测试能区分“编译成功”“测试入口成功”“测试结果文件新鲜” |

### P1：结构和可维护性

#### 1. ChatManager 继续分层

当前已把请求生命周期抽到 `ChatManager.RequestLifecycle.cs`，并已完成第一步上下文拆分：

- `ChatManager.ContextBuilder.cs`：角色卡、记忆、偏好、任务轨迹、时间天气等上下文注入（已完成第一步，暂保持 partial 以减少行为风险）。
- `ToolLoopCoordinator`：工具子集、工具回环、审批等待和结果压缩。
- `ReplyFinalizer`：回复后处理、质量检查、写入历史和遥测。

约束：缓存前缀顺序不能改变；`PromptContextBudget`、`ToolResultBudget` 和 `QualityTelemetry` 必须继续生效；拆分后先做行为对照，再做性能优化。

#### 2. ToolEngine 调度治理

- 为 `ToolRegistry` 增加安全的重复注册报告和注册快照，避免反射扫描后工具数量悄悄变化。
- 为同步工具、异步工具、危险工具建立不执行真实副作用的 mock/contract 测试。
- 统一工具失败结果的格式和日志级别，避免异常文本直接进入云端上下文。
- 保持危险工具清单与审批链单一来源，禁止在 `ChatManager`、本地路由和工具实现中各自维护一份不一致的清单。

#### 3. Live2D 参数治理

- 继续把普通动作参数迁移到 `Live2DMotionTemplates` 或语义映射配置。
- `P0` 眼睛保护、Physics 顺序、姿态锁和停止过渡保护继续保留在代码安全网中。
- 每次迁移必须做动作截图或可见播放器回归，不能只以编译通过作为完成标准。

### P2：性能、成本和观测

#### 1. Token 和云端成本

- 先按 `source/task/case_id` 收集真实 usage，再决定是否压缩上下文或改变模型路由。
- 继续保持本地模型优先、测试模式禁云端、云端失败不盲目重试。
- 对 OpenClaw 任务记录步骤数、耗时、取消原因和最终状态，区分“任务失败”和“桥接失败”。

#### 2. 运行时观测

- 为启动、桥接健康、任务提交、轮询、取消、审批和退出增加统一 correlation id。
- 日志中记录阶段、耗时和结果类别，不记录 Token、API Key 或完整敏感参数。
- 逐步把“日志搜索”变成可统计指标，减少依赖人工翻 Player.log。

#### 3. 启动依赖

- 独立整理 bridge/Gateway/Ollama 的启动、健康检查和失败恢复。
- 安装器改动单独提交，先验证全新机器、已有服务、无网络和权限不足四种路径。

### P3：暂不优先

- 3D 渲染分支：当前仍是 TODO，不纳入本轮优化。
- 全面替换 IMGUI：先解决状态和回归能力，再评估 UI 框架迁移。
- 大规模重写 `ExternalChatWindow` 或 `DesktopPet`：这两个类与 Win32、Unity 生命周期耦合较深，必须在测试覆盖增加后再拆。
- 动态分辨率全局降级：当前 Live2D RT 缩放已有性能档位入口，但主窗口分辨率策略仍保持现状，不能把“有入口”写成“已完成动态降级”。

## 四、每项优化的实施闭环

1. 先读 `AGENTS.md`、`docs/README.md`、构建规范、代码真相架构和对应模块文档。
2. 写出当前行为和目标行为，标明是否涉及云端、危险工具、外置窗口或数据写入。
3. 只做一个边界内的最小修改，并补确定性测试或运行时命令。
4. 执行 `build.ps1 -Quick`；涉及播放器、渲染、窗口或退出时追加完整构建和隔离冒烟。
5. 测试通过后再更新对应模块文档和本文状态。
6. 使用 Conventional Commit 单独提交，不把临时脚本、安装器草稿和未确认改动混入代码提交。

## 五、完成定义

一项优化只有同时满足以下条件，才可以标记为完成：

- 代码边界清楚，未引入重复安全策略或新的全局状态。
- 快速构建通过；涉及运行时的改动有完整构建和隔离冒烟记录。
- 测试使用临时数据目录，生产记忆文件 mtime 未变化。
- 失败路径、取消路径和退出路径至少有一个确定性验证。
- 文档描述的是实际验证过的代码，而不是预期收益。
- 提交信息能单独说明改动目的，后续可以回溯和回滚。
