**结论**：本地模式在成本上**完全免费**，且聊天成功率/延迟**优于**云端基线——但需注意下文局限。

## 四、主要局限与数据可信度

1. **云端组 chat 失败 8 次（89.1%）**：需查 Player.log 失败原因（超时？限流？预算拦截？），失败是否系统性影响质量对比。
2. **motion 配对不足**：预算闸门（motion 12/h + 2min 冷却）与测试节奏（9s/条）冲突 → 云端动作翻译被大量拦截。**动作质量结论不可信**，需放宽限流或延长间隔复测。
3. **云端 GLM 全 0 分**：视觉验证链路待排查，无法评估动作完成度。
4. **云端 key 归属**：消耗记在非桌宠专属 key 上（见 §一），需用专属 key 复测校准平台侧数据。
5. **评分**：本报告只有自动遥测（ok/accepted/parse/延迟），**没有人工 0-5 分盲评**（指南建议的语义/动作标准度评分）。人工评分后才能回答"质量下降多少%"。

## 五、结论（有限结论，样本口径内）

- ✅ **聊天**：本地（qwen2.5:3b）成功率 100% vs 云端 89.1%，延迟 463ms vs 4230ms——**本地在自动指标上不劣于云端**，且零成本。
- ⚠️ **动作**：本地翻译/模板成功率 100%，但云端样本被预算闸门破坏，**无法对比**。
- ❌ **视觉验证**：两组均无有效评分，链路待修。
- 💰 **成本**：本地 ¥0 vs 云端 ¥2.79/60 案例——本地优先策略显著省成本。

## 六、后续行动建议

1. **复测云端组**：用「符玄桌宠」专属 key 重跑云端组，并**临时放宽 motion 预算**（或测试专用宽松策略），补齐动作配对样本。
2. **修云端 chat 失败**：定位 8 次失败原因。
3. **修 GLM 验证**：排查 glm-4.6v-flash 全 0 分（key/链路/评分逻辑）。
4. **补人工盲评**：对 55 个 chat 配对 + motion 配对做 0-5 分盲评，计算 `(云端均分-本地均分)/云端均分`。
5. **结论更新**：补齐后重出本报告，样本 ≥30 配对时方可下"下降 X%"结论。
